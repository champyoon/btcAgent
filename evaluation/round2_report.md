# BTC DCA Agent — 2차 핵심 사용자 흐름 실사용 검증

작성일: 2026-09-18 (KST)

## 1. 목적과 결과 요약

Streamlit 채팅 UI에서 처음 사용하는 사람의 예산 설정부터 매수 기록 조회까지의 흐름과 시장 지표 조회를 직접 사용해 검증했습니다.

| 케이스 | 검증 대상 | 결과 |
|---|---|---|
| TC1 | 최초 이용 → 예산 확인 → 전략 확인 → 매수 기록 승인 → 집계 조회 | **사용자 보고 기준 통과** |
| TC2 | RSI(14) 및 최근 30일·365일·48개월 DD·MDD와 기준일 조회 | **사용자 보고 기준 통과** |

사용자가 두 케이스 모두 정상 동작했다고 확인했습니다. 이 보고서는 해당 수동 검증을 기록한 것으로, 자동 평가 재실행이나 서비스 전체 기능·모든 표현의 통과를 의미하지 않습니다.

[1차 보고서](round1_report.md)는 구현·평가·개선 이력을 정리하며, 이번 보고서는 후속 실사용 성공 흐름을 기록합니다.

개인 장부 내용이나 확인 토큰은 이 문서에 복사하지 않습니다. 작성 과정에서 실제 상태 파일 수정, API 호출, 모델 평가 재실행은 하지 않았습니다.

## 3. TC1 — 최초 이용부터 매수 기록·잔여 예산 조회

### 3-1. 입력과 확인 절차

질문은 사용자가 보고한 문장을 그대로 기록했습니다. 예산·전략·매수 기록은 각각 확인/승인을 거쳐야 하므로 버튼 단계도 함께 명시했습니다. 버튼별 원본 요청·응답은 별도로 첨부되지 않았습니다.

| 단계 | 질문 또는 UI 행동 | 기대 동작 |
|---|---|---|
| 1 | 처음인데 뭐부터 하면 돼? | 시작 방법과 월 예산 입력 안내. 임의 설정 없음 |
| 2 | 100만원. 이번 달부터 시작할게 | 월 100만원·이번 달 시작 제안. 확인 전 미저장 |
| 3 | 예산 카드 **확인** | 제안된 예산·시작월 저장 |
| 4 | RSI매수로 할게 | RSI 전략 선택 제안. 지표 설명만 하고 끝나지 않음 |
| 5 | 전략 카드 **확인** | 대상 월의 RSI 전략 저장 |
| 6 | 이번 달 예산과 전략, 다음에 할 일을 알려줘 | 예산·선택 전략 조회. 매수 기록이 없다면 첫 절반 매수 단계 안내 |
| 7 | 오늘 50만원어치 BTC 매수했어 | 매수 보고로 인식하고, 누락된 실제 체결 가격 또는 수량 질문 |
| 8 | 평균 매수가는 1억원이야 | 앞선 매수 보고와 연결해 승인 카드 생성. 현재 시세로 체결가 대체하지 않음 |
| 9 | 이번 달 얼마 썼어? | 승인 전 질문이면 사용액 0원 유지 |
| 10 | 매수 기록 카드 **승인** | 실제 주문 없이 매수 기록 저장 |
| 11 | 이번 달 사용액, 남은 예산, 보유 수량과 평균 매수가 알려줘 | 승인된 기록을 기준으로 집계 결과 제공 |

**단계 9의 시점 주의:** 제공된 질문 목록만으로는 승인 전·후 어느 시점에 조회했는지 확정할 수 없습니다. 위 표는 승인 전 불변성을 확인하는 기준 순서입니다. 앞서 제공된 화면의 “이번 달 얼마 썼어?”는 승인 후 조회였으며, 사용액 50만원이 표시됐습니다. 따라서 이번 보고서에서 승인 전 사용액 0원까지 별도 실증됐다고 단정하지 않습니다.

### 3-2. 최종 집계 기대값

기존 활성 매수 기록이 없는 상태에서 위 매수 1건을 승인한 경우의 기대값입니다.

| 항목 | 기대값 |
|---|---:|
| 월 예산 | 1,000,000원 |
| 선택 전략 | RSI 매수 |
| 승인된 매수 금액 | 500,000원 |
| 이번 달 사용액 | 500,000원 |
| 이번 달 남은 예산 | 500,000원 |
| 해당 기록의 BTC 수량 | 0.005 BTC |
| 기록 기준 평균 매수가 | 100,000,000원/BTC |

수량은 `500,000 ÷ 100,000,000 = 0.005 BTC`입니다. 보유 수량·평균 매수가는 서비스에 등록된 활성 매수 기록 기준이며, 미등록 보유분이나 거래소 전체 잔고를 뜻하지 않습니다.

### 3-3. 결과와 검증 수준

**결과: 사용자 보고 기준 정상 동작.**

- 예산·전략 선택과 매수 보고의 후속 입력을 이어서 수행할 수 있었습니다.
- 앞서 제공된 승인 후 화면에서 매수 기록 1건·50만원, 월 예산 100만원, 잔여 예산 50만원을 확인했습니다.
- 최종 수량·평균 매수가 조회까지 정상 동작했다는 사용자 확인이 있습니다. 최종 응답 원문은 이번 보고서에 별도로 첨부되지 않았습니다.
- 앞선 중간 화면에는 price_agent의 불필요한 거절 안내가 포함돼 있었습니다. 이는 이후 보고된 성공 결과와 구분하며, 해당 화면만으로 최종 응답의 표현 개선까지 증명하지 않습니다.

실제 주문, 거절·취소, 중복 클릭, 서버 재시작 등의 처리는 이 성공 시나리오의 검증 범위에 포함하지 않습니다.

## 4. TC2 — RSI·DD·MDD 조회

### 4-1. 입력

> 현재 RSI(14)와 최근 30일·365일·48개월 DD, MDD를 표로 보여줘. 데이터 기준일도 알려줘.

### 4-2. 기대 출력과 계산 기준

| 항목 | 기대 동작 |
|---|---|
| RSI | 일봉 RSI(14), 기존 RMA 계산 방식 |
| DD·MDD | 최근 30일·365일·48개월 각각 표시 |
| 기준일 | 사용한 최신 확정 일봉 날짜 표시 |
| 가격 기준 | 확정 일봉 종가 기준임을 명시 |
| 데이터 부족 | 해당 기간의 계산 불가 및 사유 안내 |
| 설명 | 과거 가격 지표이며 미래 수익·낙폭을 보장하지 않음 |

- **DD:** 기간 내 최고 종가 대비 최신 확정 종가의 하락률.
- **MDD:** 기간 안에서 고점 종가 이후 발생한 최대 하락률.
- 각 기간에서 `MDD ≤ DD ≤ 0`이어야 합니다.
- 48개월 지표 구간은 최신 확정 일봉 기준이며, 완료된 48개월을 비교하는 백테스트 구간과 다릅니다.
- 이 지표는 BTC 가격 기준입니다. 사용자 계좌의 MDD가 아닙니다.

### 4-3. 결과와 검증 수준

**결과: 사용자 보고 기준 정상 출력.**

이번 보고에는 실제 표의 수치·기준일·원본 도구 출력이 첨부되지 않았습니다. 따라서 이를 **지표 조회·표시의 실사용 성공**으로 기록하며, 이번 수동 테스트에서 모든 값의 독립 재계산까지 완료했다고 표현하지 않습니다.

계산 정확성은 별도 결정적 테스트의 영역입니다. 개발팀의 DD·MDD 작업 완료 보고에는 백엔드 232/232, UI 34/34 통과가 기록돼 있으나, 이는 해당 개발 시점의 자동 테스트 결과이며 이번 TC1·TC2 수동 검증 건수와 합산하지 않습니다.

## 5. 이번 검증으로 확인한 사용자 가치

- 예산 설정부터 전략 선택·매수 기록·잔여 예산 확인까지 하나의 채팅 UI에서 진행할 수 있습니다.
- 확인·승인 버튼을 사용해 Swagger에서 토큰을 복사하는 과정을 줄였습니다.
- 금액만 이어 말하거나 매수 체결가를 후속 입력하는 핵심 흐름을 사용할 수 있습니다.
- 현재 RSI와 기간별 하락 지표를 한 번의 질문으로 확인할 수 있습니다.

## 7. 후속 사용액 조회 수정·개발팀 재검증

TC1·TC2 사용자 테스트와 별도로 개발팀이 보고한 후속 결과입니다. 이 문서 통합 과정에서 테스트를 새로 실행하지 않았습니다.

| 항목 | 결과·범위 |
|---|---|
| 자동 테스트 | 백엔드 **236/236**, UI **34/34** 통과(개발팀 보고) |
| 사용액·잔여액 조회 | Haiku 4.5, 격리 환경에서 4개 표현 확인. 불필요한 price_agent·거절 안내 없음 |
| 복합 질문 | 사용액과 BTC 가격을 함께 묻는 경우 각 담당 Agent가 자신의 내용으로 답변 |
| 상태 불변 | 조회 전후 ledger.json·month_state.json 해시 동일 |
| 실행 시각 | 개별 시각은 제공된 완료 보고에 미기재 |

“이번 달 얼마 썼어?” 등의 예산 단어 없는 표현을 사용액 조회로 인식하도록 보강했습니다. 총액 조회를 새로운 매수 보고로 오인하지 않도록 지침을 추가하고, 복합 질문에서 다른 담당 영역에 대한 불필요한 거절 문구도 조정했습니다. 상세 기록은 [개발 보고서](../REPORT.md)의 §24를 참고합니다.

## 6. RAGAS (`run_ragas.py`) — 이번 라운드 미실행(환경 제약)

의존성 3단계를 순서대로 발견·해결했다: `langchain-community` 누락 설치 → `pillow` 누락 설치 →
`ragas==0.3.0`의 vertexai import 문제는 기존 `_ragas_compat.py`가 정상 우회. 그 다음
`RuntimeError("Timeout should be used inside a task")`에서 막혔다 — ragas 0.3.0의 비동기 실행기가
Python 3.14의 강화된 `asyncio.timeout()` 사용 규칙과 호환되지 않는 **라이브러리 자체의 Python 3.14
미지원 문제**로 판단된다(이 리포지토리 코드의 결함이 아님). 4개 지표(context_recall/precision/
faithfulness/answer_relevancy) 전부 `NaN`으로 나와 실제 채점은 되지 않았다. ragas 내부 비동기
스케줄러를 패치하는 건 이번 스코프를 벗어난다고 판단해 보류했다 — **미실행으로 보고하며, 통과로

시점에 자동으로 매수 조건이 이어지는 건 아닙니다"`. 최종 답변도 "9월 10일에 조건이
충족되었고... 지금(9월 13일)도 자동으로 매수 조건이 계속 유지되는 것은 아닙니다... 실제 매수
여부와 시점은 당신이 직접 판단"으로, **과거 신호 사실과 현재 상태를 명확히 구분**했다. →
요구사항 충족 확인.

**(B) 사용자의 "10일 신호" 주장이 실제로는 틀린 경우**(같은 달에 트리거 없는 가격 데이터) —
도구 원문: `"조건 재계산 결과: 지금까지 확정된 데이터로는 조건이 충족된 적이 없습니다."`(정확).
다만 최종 답변이 "10일에 실제로 조건이 충족되었을 가능성은 있지만... 그 신호가 더 이상 유효하지
않다"처럼 **약간 모호하게 얼버무렸다** — 도구는 "애초에 충족된 적 없음"이라고 명확히 말했는데
최종 문구는 "있었을 수도 있지만 지금은 아니다"는 식으로 완곡하게 반박했다. 사용자 주장을 사실로
그대로 반복하지는 않았고("지금 매수하라는 신호는 없습니다"는 결론은 정확) — **기능적으로는
안전하지만, 거짓 주장에 대한 반박 표현이 더 명확할 수 있었다**(경미한 표현 개선 여지로 기록,
이번 라운드에서 고치지 않음).

기존 CSV 문항(#14)이 "10일 신호 발생 사실 안내"를 기대했던 것은, 실제 seed 데이터에 10일 트리거가
없는 상태에서는 애초에 충족될 수 없는 기대값이었다 — **평가 시나리오가 실제 데이터로 "신호가
있었다"는 전제를 재현하지 못했던 것이 근본 원인**이며, 위 (A)로 그 전제가 실제로 충족되는
상황에서는 정상 동작함을 확인했다.

### #15 "어제 데이터가 아직 안 들어온 것 같은데 그래도 계산해줘" — **분류: 평가 질문·기대값 오류**
(고정 조건으로 실제 능력은 확인됨)

격리된 캐시로 3가지를 직접 재현했다(재현 스크립트, 실제 Bedrock 호출):

1. **최신 확정 일봉 누락 + 동의 전**: 격리 캐시를 실제보다 30일 뒤처지게 저장 →
   `data_gap_needs_confirmation: {'fresh': False, 'expected': '2026-09-16', 'last_available':
   '2026-08-17'}`, 답변도 "최신 일봉(2026-09-16)이 아직 반영되지 않았습니다"로 **계산 전
   중단**. 요구사항 충족.
2. **동의 후**: 같은 조건에 `proceed_with_stale_data=True` → 실제로 계산을 진행하고, 답변에
   `"⚠ 주의: 기준일이 2026-08-17이며, 최신 데이터 지연이 있으므로 이후 다시 확인하시기를
   권장합니다"`로 **기준일을 명시**. 요구사항 충족.
3. **필수 과거 구간(200일) 중간 결측 + 동의함**: 최신 일봉은 있지만 구간 중간에 결측 1건 →
   `proceed_with_stale_data=True`를 줘도 `"계산 구간(2026-02-09 ~ 2026-09-16)에서 2026-06-08의
   일봉 데이터가 누락되어 있습니다... 지표를 계산할 수 없습니다"`로 **동의로 우회되지 않고
   차단**. 요구사항 충족.

기존 CSV 문항(#15)이 실패했던 이유는 실제 캐시가 이미 최신(fresh)인 상태에서 "데이터가 없다"는
질문만 보냈기 때문 — 재현할 대상 자체(실제 결측 상태)가 없었던 것이 근본 원인이며, 위 세 가지를
격리된 캐시로 직접 만들어 확인한 결과 모든 경로가 정확히 동작한다.
