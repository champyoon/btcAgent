# BTC DCA Agent — 자체 평가 및 개선 보고서
작성일: 2026-09-17 (KST)

## 1. 서비스와 구현 범위

**매월 정한 예산으로 BTC를 모으는 사용자가 전략을 비교하고, 매수 조건과 실제 기록을 관리하도록 돕는 에이전트입니다.** 가격 조회·계산·장부 정리를 하나의 질의 흐름으로 연결합니다. 실제 거래소 주문은 사용자가 직접 진행합니다.

월 예산의 절반은 1일에 매수하고, 나머지 절반은 다음 세 방식 중 사용자가 선택합니다.

| 방식 | 조건 |
|---|---|
| 하락일 매수 | 확정 일봉 종가가 시가 대비 5% 이상 하락하면서 이번 달 첫 매수가보다 낮음 |
| 정기 분할 | 매월 15일 매수 |
| RSI 매수 | RSI(14, RMA 방식)가 30 이하 |

조건부 전략의 백테스트는 조건 충족 다음 날 시가로 매수하며, 월말까지 남은 예산은 마지막 날 시가로 매수합니다. 직전 달까지 완료된 48개월을 동일 예산으로 비교하고, 수수료·슬리피지는 0으로 가정합니다. 과거 결과를 미래 수익 보장이나 자동 전략 선택으로 사용하지 않습니다.

MVP는 로그인 없는 1인용이며, FastAPI·Swagger로 이용합니다. 월 예산·전략 제안/확인, 매수 기록 생성·수정·취소, 관망 기록, 평균 매수가·남은 예산 조회를 지원합니다. 상세 기획은 [SERVICE.md](../SERVICE.md), 계산·정책 명세는 [SPEC.md](../SPEC.md)를 참고합니다.

## 2. 에이전트·도구·RAG·가드레일·트레이스

Supervisor가 질문을 라우팅하고, 필요한 전문 Agent의 도구 호출과 답변을 조립합니다. 네 Agent는 서로 다른 역할·도구를 사용하며 기본 응답 모델을 공유합니다.

| 구성 | 역할 | 주요 계산·도구 모듈 |
|---|---|---|
| price_agent | 현재가·확정 일봉 기반 지표 조회 | tools.py, price_history.py, indicators.py |
| plan_agent | 월 예산·전략·조건 재확인·48개월 백테스트 | month_state.py, strategy.py, backtest.py |
| ledger_agent | 사용자 매수·관망 기록과 집계 | ledger.py |
| research_agent | BTC·DCA·RSI·서비스 규칙 설명 | retriever.py, data/docs/ |

네 Agent(price/plan/ledger/research)의 정의(시스템 프롬프트·도구 바인딩·라우팅 키워드)와 Supervisor
(라우팅, 도구 실행 흐름, 최종 답변 조립)는 모두 `src/agent.py` 한 곳에 있습니다. 위 표의 "주요
계산·도구 모듈"은 각 Agent가 호출하는 하위 계산/저장 모듈이며, Agent 자체가 그 모듈에 정의돼 있다는
뜻이 아닙니다.

- **데이터:** Upbit KRW-BTC 실제 가격·일봉을 로컬 JSON 캐시에 저장합니다. 가격 계산과 문서 검색 저장소를 분리합니다.
- **RAG:** 문서를 Chroma에 색인하고 검색된 근거로 설명합니다. 문서 내용·청킹 설정·임베딩 모델의 지문으로 재색인 여부를 판단합니다.
- **계산:** RSI·전략 조건·예산·백테스트 수치는 Python 도구가 계산합니다.
- **가드레일:** 지원 범위·개인정보·규칙 우회 요청을 처리합니다. 승인 ID 대상은 **매수 기록 생성·수정·취소·장부 초기화**이며, 서버에 보관한 승인 ID로 한 번만 실행합니다. **관망 기록은 승인 없이 즉시 저장**합니다. **예산·전략은 승인 ID 대상이 아니라 별도의 제안→확인→저장 절차**(각자의 확인 토큰, `/confirm_budget_change`·`/confirm_strategy_change`)를 거쳐야 저장됩니다.
- **데이터 확정성:** KST 09:00 일봉 경계에 따라 마감된 데이터만 사용합니다. 최신 데이터 누락 시 확인을 요청하며, 필수 계산 구간 결측은 동의로도 우회하지 않습니다.
- **트레이스:** 응답의 trace·agents_used·contexts 등으로 라우팅, 도구 호출, 검색 근거를 확인합니다.
- **MCP:** 이번 MVP에서는 사용하지 않았습니다. API와 Python 도구를 직접 연결했습니다.

## 3. 평가 방법과 결과

### 3-1. 서로 다른 검증의 역할

| 평가 | 확인하는 내용 |
|---|---|
| pytest | 계산 경계, 상태 변경, 승인 경합, 캐시·결측 처리, 응답 조립 |
| 규칙 기반 인-아웃 평가 | 기대 도구 호출·거절·응답 항목 |
| LLM-as-Judge | 답변의 정확성·일관성·설명 품질 |
| RAGAS | 검색 근거의 관련성·포괄성, 답변의 근거 충실도·질문 관련성 |
| 실제 /query 검증 | 모델과 도구가 연결된 사용자 흐름 |

### 3-2. 결과와 적용 범위

**아래 결과는 같은 코드 버전에서 한 번에 실행한 종합 성적이 아닙니다.** 이전 평가와 최신 변경의 검증 범위를 구분합니다. 본 제출 보고서 작성 과정에서 유료 LLM 평가나 pytest를 새로 실행하지 않았으며, 저장된 결과·코드·개발팀 최종 보고를 대조했습니다.

| 검증 | 모델 | 결과 | 근거·범위 |
|---|---|---|---|
| 최신 코드 테스트 | LLM 호출 없음 | **142/142 통과** | 개발팀 최종 보고 및 REPORT §15-7·§16·§17·§18·§18-2·§19. 예산 제안 자유 서술 제외 회귀 테스트, 시작 안내 라우팅 회귀 테스트, 드로다운 고점 발생일 회귀 테스트, 매수 시기 질문(1·2차 표현 변형)·예산 결정 표현 라우팅 회귀 테스트 포함 |
| 규칙 기반 평가 | Haiku 4.5 응답 | **22/22 통과** | 개발 round4의 당시 22문항·코드 기준 |
| LLM-as-Judge | 응답·채점 모두 Haiku 4.5 | **19/22 통과** | 개발 round4 기준. 최신 변경 후 전체 재채점 아님 |
| RAGAS | 응답·채점 모두 Haiku 4.5 | **8/8 실행 완료**, 오류·NaN 0건 | 저장 JSON 실행 시각 2026-09-17 13:30:22 KST |
| 최신 최초 이용 질문 /query | Nova-pro | **개발팀 보고상 통과** | 2026-09-17 16:15:36 KST. 서비스 설명 유지·예산 안내 중복 제거 |
| 시작 안내("뭐부터 해야 해?") /query | Nova-pro | **개발팀 보고상 통과** | 초기 상태(계획 없음): 2026-09-17 16:27:59 KST, `get_month_status`만 호출·저장 상태 무변화. 예산·전략 기설정 상태: 같은 점검에서 이어서 확인(개별 실행 시각은 기록되지 않음), 마찬가지로 `get_month_status`만 호출·저장 상태 무변화 |
| 지표 조회("현재 btc 지표 알려줘") /query | **Haiku 4.5**(global 프로파일) | **개발팀 보고상 통과** | 2026-09-17 16:59:09 KST, 격리 환경. 드로다운 고점 발생일 오설명(§4 참고)을 실제 이 모델 응답에서 발견·수정 후 같은 질문으로 재확인 — 이 세션 최초의 제출 모델 자체 실검증 |
| 최초 이용 원문("처음 쓰는데 어떤 서비스야?...") /query | Haiku 4.5 | **미완료·대기** | 이전엔 `us.` 프로파일의 일일 토큰 쿼터 소진으로 응답 자체를 못 받았음. 2026-09-19 이후 같은 모델의 `global.` 프로파일로 전환해 Haiku 자체는 접근 가능해졌으나(위 지표 조회 행 참고), 이 원문 그대로의 재실행은 아직 하지 않음 |

현재 기본 모델은 Haiku 4.5이며, 2026-09-19부터 `global.` 리전 프로파일(`global.anthropic.claude-haiku-4-5-20251001-v1:0`)을 씁니다 — 같은 모델의 `us.` 프로파일이 일시적으로 막혀 전환한 것으로, 모델 자체를 바꾼 것은 아닙니다. 모델 선택은 고정 과제 조건이 아니며, 다른 모델로 시험할 수 있지만 모델별 결과를 섞어 보고하지 않습니다.

**최근 수동 테스트 중단**: 수동 확인 중 "다음달 예산은 얼마야?" 질문이 Bedrock `ThrottlingException`
(오류 메시지: "Too many requests", `reached max retries: 4`)으로 응답을 받지 못해 중단됐습니다. 이
메시지만으로는 일일 토큰 쿼터 소진인지 순간적인 요청 빈도 제한인지 단정할 수 없어(별개 축으로 알려진
두 가지 원인이 있음), 원인을 확정하지 않습니다. 이 중단을 예산 저장 실패나 계산 결함으로 분류하지
않고, **해당 조회 및 그 수동 확인 흐름의 검증이 완료되지 못하고 중단된 것**으로만 구분합니다.

기존 22문항에서 규칙 기반 결과는 positive 10/10, negative 4/4, edge 5/5, guardrail 3/3입니다. LLM-as-Judge는 총 3건이 미통과였고, 후속 검토에서 설명의 모순·불명확성과 평가 시나리오의 전제 불일치를 구분했습니다. 실패를 사후에 모두 통과로 환산하지 않았습니다. 현재 CSV에는 예산 확인 문항이 추가되어 있으므로 **22/22를 현재 평가 세트 전체 통과로 해석하면 안 됩니다.**

**SERVICE.md 성공 기준 대비**: positive 80% 이상·negative/가드레일 100%·필수 pytest 전부 통과라는
목표는, round4 시점의 22문항·코드 기준으로 충족됐습니다(positive 10/10=100%, negative 4/4=100%,
guardrail 3/3=100%, 당시 pytest 전부 통과). **이건 "당시 기준 목표 충족"이며, 최신 코드 전체에
대한 재검증 완료를 뜻하지 않습니다** — 위 표의 142/142는 최신 코드의 결정적 계산 테스트 전체
통과를 의미하지만, 규칙 기반·LLM-as-Judge는 여전히 round4(22문항) 기준 수치이고 최신 추가 문항까지
포함해 다시 채점하지 않았습니다.

### 3-3. RAGAS 기준선

| 지표 | 평균 | 의미 |
|---|---:|---|
| context_recall | 1.00 | 기준답변에 필요한 내용이 검색 근거에 포함되는 정도 |
| context_precision | 0.77 | 검색 결과의 관련성과 순위 품질 |
| faithfulness | 0.67 | 생성 답변이 검색 근거로 뒷받침되는 정도 |
| answer_relevancy | 0.55 | 답변이 질문에 관련되는 정도 |

8문항은 BTC·DCA·RSI 정의, RSI의 한계, 전략 조건, 월말 처리, 백테스트 해석으로 구성했습니다. 실시간 가격이나 개인 상태는 이 세트에서 제외했습니다.

**8/8은 실행 완료 수이지 품질 만점이 아닙니다.** 특히 근거 충실도와 질문 관련성은 개선이 필요합니다. 검색된 정보가 있어도 불필요한 설명이나 근거 밖 문장이 섞일 수 있습니다. 동일 모델로 생성과 채점을 수행했고 문항 수도 작아, 서비스 전체 품질로 일반화하지 않습니다.

결과 JSON은 응답·채점·임베딩 모델, 실행 시각, 평가 세트 해시와 코드 표기 `06b3081+dirty`를 보존합니다. dirty 표기만으로 당시 미커밋 변경 전체를 재현할 수는 없으며, 최신 코드와 동일하다는 뜻도 아닙니다.

## 4. 발견한 문제와 개선 사이클

| 문제 | 원인 | 수정 | 검증·남은 한계 |
|---|---|---|---|
| 미마감 일봉이 확정값으로 사용됨 | 저장 시 마감 여부를 검사하지 않고 최신 날짜만 비교 | 저장 전 확정성 필터, 전체 레거시 캐시 재수집·검증 후 원자적 교체, 결측 검사 연결 | 개발 보고에 실제 종가 정정과 회귀 테스트 기록. 여러 과거 일봉이 오염됐다는 이전 주장은 근거 부족으로 철회 |
| RAG 검색 결과에 같은 청크가 반복됨 | 재시작 때 인덱스에 중복 추가 | 내용·설정·모델 지문으로 재사용/재구축 결정 | 무변경·같은 청크 수의 내용 변경·문서 삭제 테스트 |
| RAGAS 질문과 기준답변 불일치 | CSV 행 번호 기반 매핑이 문항 변경을 따라가지 못함 | 고정 ID의 전용 평가 세트 분리, 필수 필드·문서 검증 | 8문항 실행 완료. 이전 오류 점수와 성능 향상률 비교 안 함 |
| 최초 이용 질문이 범위 밖으로 거절됨 | 서비스 소개·예산 의도를 라우팅하지 못함 | 서비스 소개 표현과 금액+반복 주기 인식 보강 | 원문 실제 호출·표현 변형 테스트. 예시 설명과 설정 요청 구분 |
| 예산 제안인데 “설정 완료”, “2주마다 자동 매수” 등 오설명 | 자유 서술에 상태·규칙 안내를 맡김 | 예산 제안 시 plan_agent 텍스트를 제외하고 도구 결과로 안내 생성 | 잘못된 문구를 직접 넣는 회귀 테스트, Nova 실제 호출. Haiku 재검증 대기 |
| 동시 승인 시 중복 실행 위험 | 구현 세부사항에 의존한 동시성 처리 | 명시적 Lock과 상태 전이 검사 | 승인·거절 경합 테스트. 프로세스 메모리 방식의 한계는 유지 |

핵심 개선은 프롬프트 수정에만 의존하지 않고, **계산·상태 변경·승인·예산 안내처럼 정확성이 필요한 부분을 코드와 구조화된 결과로 통제한 것**입니다. 다른 Agent의 모든 자유 서술까지 정확성이 보장된다는 의미는 아닙니다.

## 5. 사용 흐름과 확인 방법

대표 질문: **“처음 쓰는데 어떤 서비스야? 매달 200만원씩 투자하고 싶어.”**

1. /query가 서비스 설명과 월 예산 제안을 반환합니다.
2. 응답에 금액·적용월·아직 미저장인 상태와 확인/취소 방법이 표시됩니다.
3. 반환된 confirmation_token으로 /confirm_budget_change를 호출해야 실제 저장됩니다.
4. 월 상태 조회로 반영 결과를 확인하고, 전략 비교·선택과 매수 기록 흐름을 이어갑니다.

수동 검증은 BTC_AGENT_DATA_DIR로 실제 장부와 분리한 환경에서 진행했습니다. 세부 실행 순서와 예상 결과는 [수동 테스트 가이드](manual_test_guide.md)를 참고합니다. Swagger API는 무상태이므로 단순히 “네”라고 재질문하는 것과 확인 API 호출은 다릅니다.

## 6. 남은 검증과 다음 단계

- **Haiku 최신 실 대화 재검증:** `global.` 프로파일 전환으로 Haiku 4.5 자체는 다시 접근 가능해졌고(§3-2 지표 조회 행 참고), 이후 매수 시기 질문 라우팅 수정(§4 표)과 예산 결정 표현 라우팅 수정(§4 표)도 각각 이 프로파일로 실제 재확인했습니다 — 남은 건 쿼터 회복 대기가 아니라, 원래 최초 이용 질문 원문과 예산 확인→상태 조회 흐름을 이 프로파일로 실제 재실행하는 것입니다.
- **현재 평가 세트 재실행:** 추가된 예산 확인 문항과 최신 프롬프트·응답 조립·채점 기준을 반영해 모델과 코드 버전을 기록합니다. 새 confirmation_flow_accuracy 기준의 실제 채점도 대기 상태입니다.
- **RAG 품질 개선:** 월말 처리·백테스트 설명 등 낮은 점수 문항의 답변과 근거를 대조하고, 중복·모순·근거 밖 설명을 줄입니다.
- **복합 질문 점검:** 예산 제안 시 plan_agent 자유 서술을 제외하므로 다른 계획 질문이 함께 들어왔을 때 필요한 답변이 빠지지 않는지 추가 확인합니다. 전략 제안에는 같은 제외 처리가 적용되지 않았습니다.
- **MVP 한계:** 로그인·자동 주문·알림·채팅 UI는 없습니다. 대기 승인·확인 토큰은 서버 재시작 시 사라지며, 여러 서버 프로세스 간 공유 저장소도 아닙니다.

**결론:** 핵심 기능 구현과 반복 평가·수동 테스트를 통해 데이터·검색·승인·답변 결함을 개선했습니다. 다만 최신 코드의 전체 모델 평가와 일부 답변 품질 개선이 남아 있어, 서비스 전체 검증 완료로 선언하지 않습니다.
